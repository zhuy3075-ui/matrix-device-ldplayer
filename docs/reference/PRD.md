## 1. 背景、目标与角色

两款产品共同解决“电脑识别Android设备、观察其状态、执行操作”的问题：调试工具帮助开发/测试人员定位界面节点与操作参数；云控帮助设备操作人员组织多设备、同步输入、运行脚本，并向外部程序提供API。

产品目标是让设备身份、连接状态、操作目标、执行进度和失败原因可见。原程序的商业登录/额度准入存在代码依据；服务端规则未恢复，不纳入可独立复刻的业务承诺。

用户角色：调试人员（单设备观察与验证）、设备操作人员（分组和批量操作）、集成人员（HTTP/脚本接入）。没有足够证据反推完整多角色权限体系。

## 2. 范围与非目标

反推范围涵盖桌面UI、设备发现、投屏输入、节点调试、应用/文件、群控输入、脚本与API、配置日志；代理/资料备份作为云控扩展能力记录。手机端系统、ROM、内核、商业服务端，以及广告中的检测通过率不作为已实现验收结果。

此前用户提出的20台ADB设备是拟建产品的容量目标；样本没有本次20台测试证据。不能把该目标写成目标软件的实测成绩。

## 4. 关键用户流程

调试：选设备 → 连接自动化/投屏 → 刷新截图与Dump → 选节点查看属性 → 执行Shell或导出结构 → 查看结果。选择节点与点击手机是不同动作，界面不得混淆。

群控：发现设备 → 分组/选择目标 → 打开主控 → 选择鼠标/键盘同步 → 操作 → 观察各目标状态。切换主控时，旧generation事件不应误投到新会话。

脚本：导入ZIP包 → 校验manifest/steps → 设置参数 → 选设备 → 运行 → 查看日志 → 停止。样本的Pause实质是取消，新实现不得承诺无证据的断点恢复。

API：配置监听端口 → 启动相应服务 → 查看每设备地址/状态 → 外部客户端按契约调用 → 返回结构化结果。普通API与Automator的字段和错误封装必须分别展示。

## 5. 非功能约束、风险与失败模式

- 响应性：网络/解码/脚本不阻塞WPF交互；使用Dispatcher更新UI。静态有异步/队列证据，但无实测延迟目标。
- 顺序：同一设备的控制必须保序；MOVE可以合并，DOWN/UP/按键边界不能随意丢弃。
- 资源：离线、取消、连接失败均清理会话/转发/缓冲所有权；按设备隔离错误。
- 兼容性：调试版与云控版Core/JAR分别校验；不可假定文件名相同就协议相同。
- 数据：恢复应用资料、清数据、卸载属于用户可见破坏性动作；确认应显示设备与包名。
- 日志：保留serial/阶段/结果，控制敏感内容；原程序部分日志路径是空实现或可空回调，不能以“没有日志”判定成功。
- 容量：20台目标需逐级试验，不预设CPU/GPU、网络与手机性能。

## 6. 验证计划及方案取舍

先做离线契约测试（API路由/DTO、包格式、坐标/事件序列、配置恢复），再专用设备单台验证，随后5台及20台。记录连接率、掉线恢复、输入延迟分布、CPU/GPU/内存、帧率和脚本取消延迟；阈值由实际硬件基线确定后再批准。

| 方案                                | 复杂度/测试与维护           | 风险与迁移成本                   | 判断                           |
| --------------------------------- | ------------------- | ------------------------- | ---------------------------- |
| 推荐：独立实现设备编排、UI和API，采用可维护的投屏/自动化组件 | 中；集中测队列、协议和状态       | 明确版本适配；旧配置需显式映射           | 适合20台群控目标，避免把商业账号/ROM能力带入MVP |
| 更简单：现有投屏工具 + 小型ADB脚本/API服务        | 低；单屏和基础动作验证较快       | 多屏体验/节点调试较弱；以后可能重做UI      | 适合先证明设备与脚本流程                 |
| 拒绝：把两套混淆DLL任意混用后直接交付              | 初始接线似乎较少，后续定位和回归成本高 | 同名不同协议/资源、未知生命周期；迁移受原格式绑定 | 无充分兼容证据                      |
| 完整复制所有扩展功能                        | 高；代理、备份、系统环境矩阵很大    | 涉及root/设备数据，ROM依赖重        | 超出第一版主目标                     |

推翻推荐的条件：单台协议兼容都无法稳定实现；20台基准显示解码/传输瓶颈无法满足明确阈值；业务实际只需少量基础操作；或后续证明主要依赖定制ROM而非桌面编排。此时缩小功能或更换底层组件，不把静态逆向推导当作必然可行性证明。
