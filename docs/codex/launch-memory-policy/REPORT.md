# 启动内存检查修正

本报告记录历史策略与当时的验证，不代表当前确认条件。2026-10-15后续已改为仅明确容量不足才确认，并补充同实例虚拟机RAM来源；最新规则见[启动资源确认修复](../launch-resource-confirmation/REPORT.md)。历史事实与原始结论不追溯改写。

## 目标与根因

- 用户问题：雷电自身可以启动，但群控因可用内存不足11 GiB而拒绝。
- 已知事实：旧桌面代码用11 GiB和80%作为统一硬门槛，没有读取目标实例内存。这不是雷电官方最低要求。
- 目标：按实例配置逐台评估；经验值仅用于风险提示，不能冒充不可启动的结论。
- 非目标：不修改模拟器内存配置，不更换/重启ADB，不操作原实例0，不启动批次外实例，不改变监控视频实现。

## 方案与取舍

- 推荐方案：只读实例配置文件，使用Windows物理内存、可用提交额度和负载快照；冷启动前逐台重新评估。已运行实例直接跳过资源检查。
- 物理内存建议值：配置内存 + 512 MiB进程开销估计 + 1024 MiB系统预留估计。可用提交额度建议值：配置内存 + 512 MiB。负载90%起提示。这些都是可被现实运行数据推翻的经验估计，不是精确预测。
- 低于建议值或信息未知：说明原因并让用户决定是否仍然启动。取消停止后续，不关闭已运行实例。资源足够时不增加弹窗。
- 更简单方案：直接删除全部资源检查。虽可消除误拦截，但批量多开时缺少风险提示，未采用。
- 拒绝方案：仅把11 GiB改成较小的固定值，或自动扩大虚拟内存。前者仍与实例配置无关，后者超出范围并涉及系统设置。
- 成本：增加一个只读配置解析器和小型纯策略；CLI身份/代次核验及串行启动逻辑继续复用。无数据迁移。
- 失败模式：厂商配置格式变化或缺省字段会触发未知提示；内存可能在检查后被其他进程消耗；用户继续高风险启动仍可能卡顿或失败。不能据此承诺启动一定成功。
