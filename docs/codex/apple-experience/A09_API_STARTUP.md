# A09b1 接口启动一致性

## 背景与目标

基线 `6bad800`。设置工作区已交付，本阶段推进原R06和A09的接口正常/异常路径，不替代完整GUI、扩展工具和实机验收。静读发现：`MatrixRuntime.StartApisAsync`任一步失败都会调用`Api.StopAsync`，后者会停止全部网关和设备接口。此前只验证全冷启动首端口冲突，尚未验证补启失败不破坏既有服务。

目标是让“一次启动两个网关”在失败时只撤销本次新增的监听，不停止之前已经运行的网关或设备接口；保留原启动异常，使用户可修正端口后重试。

## 范围与非目标

- 仅修改Host的网关启动协调与Runtime委托，以及正式回归测试；复用现有Kestrel、端口验证、日志、同Runtime与生命周期锁。
- 不改HTTP路由/响应、监听范围、认证或授权、单网关公开方法、全部停止和Runtime释放语义；不新增第二套运行时或后台服务。
- 不操作真实模拟器、ADB、用户API、账号、代理、VPN或配置。仅fresh Demo Runtime和自有loopback监听；不终止占用端口的其它进程。
- VM部分失败后的状态刷新、API页面布局、请求测试、扩展工具与原生对话框另属后继；本阶段通过不代表完整A09或GUI通过。

## 第一性原理与方案

已知事实是启动和停止已共享`ApiServiceManager`生命周期锁，但Runtime的两个启动调用分开获取该锁，失败后又全局停止。根问题是事务的资源所有权和锁边界不一致，不是错误文案。

推荐由Runtime先冻结同一份Settings的两个端口，再在Manager的同一次生命周期锁内协调两网关，复用原启动实现；记录本次新建监听，仅在失败时回滚该具体实例。既有同端口监听保持幂等，既有不同端口仍拒绝；所有设备接口保留。不得在持锁期间调用会再次获取同一锁的公开启动方法。回滚不沿用已取消的启动令牌；Stop/Dispose错误不能互相覆盖或掩盖最初的启动失败。若Dispose失败则保留具体owner供显式停止，私有待清理标记阻止后续启动把未知状态误当幂等成功；原全部停止清字段时复位该标记，不改变停止范围。这里的原子性仅指生命周期修改串行及失败后的状态，不宣称两个socket瞬时同时可见。

更简单的VM `finally`刷新只能修显示，无法阻止既有服务被停。仅删除回滚则改变冷启动失败的既有语义，可能留下新服务，故不采用。另建Runtime锁或启动前读取bool再跨多个独立加锁调用，不能与Manager公开启停串行，也不采用。

失败模式包括：第二端口占用、既有端口与新配置冲突、取消发生在任一步、并发启动/停止、回滚释放异常。测试必须检查实际HTTP和监听端口，不仅检查bool；未取得可控释放异常的证据时不得声称该注入场景通过。

## 验收标准

1. P0：独立测试先在旧生产代码经公开方法复现“既有普通网关和设备接口被补启失败关闭”；自有TcpListener占用第二端口，不改测试断言取得通过。
2. P1：全冷启动成功，两网关实际health可读；相同配置重复启动保持端口、服务及设备接口。
3. P1：全冷启动第二端口冲突时，本次新建普通网关被撤回；原有设备接口及占用端口的自有监听保持。释放占用后可重试，未停止已有第三方服务。
4. P1：已有普通网关，补启自动化失败后，原网关和设备接口仍同端口、health成功；已有自动化网关时，第一个启动失败或第二个端口不匹配不得关闭它。
5. P1：既有普通/自动化配置端口不匹配仍拒绝，任何既有服务保留；取消与并发调用服从同一生命周期边界，不使用sleep猜测事务时序。
6. P1：原225项名称、顺序和断言保留，新增用例单列；所有自有HTTP任务、监听、Runtime和输出流有终态，真实环境与主仓保护文件不变。
7. P1：非实现者审查源码和实际红绿证据，主仓集成后复验；更新README/任务/报告和源码清单，独立核包、精确暂存后按原授权单项推送私有开发分支，不合并发布。
