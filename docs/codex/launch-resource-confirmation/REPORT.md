# 启动资源确认修复

日期：2026-10-15。状态：实现、主工程与最终独立验证通过，无未闭合阻断。只使用项目本地上下文，不读取CODEBRAIN。此结论不扩展为真实冷启动成功率验收。

## 目标与根因

用户要求修复RAM未知导致的弹窗，仅在明确资源不足时保留确认。旧策略把配置未知、采样失败、高负载与低于经验预留都当成弹窗依据，混淆了诊断信息和可观察的容量不足。

只读调研发现：专用实例1的JSON没有内存字段，但同编号vms/leidian1/leidian.vbox当前Machine/Hardware/Memory@RAMSize为6144；实例2两处均为2048。不能从全局模板、快照或所谓默认2GiB猜测。

## 范围与验收

- 有效实例RAM和主机容量快照同时存在，且可用物理内存或可用提交额度严格小于配置RAM时，显示资源不足确认；等于RAM不弹。这仍不是官方启动限制或成败保证。
- RAM缺失、冲突、读取失败、主机采样未知只显示诊断，不弹窗、不伪造0/默认RAM，不声称资源已充足。
- 高负载或仅低于512 MiB开销/1024 MiB系统预留等估算余量，不单独触发确认；若同时存在明确容量不足，仍须确认。
- 负载字段异常不抹掉另外两个已知容量数值，单独显示负载未知。采样为快照，不代表资源预留。
- 取消确认停止后续启动，已运行实例不变；已有实例仍跳过冷启动资源检查。原0/99999、身份/代次与共享服务保护不变。
- 不更改模拟器配置，不启动/关闭实例，不动ADB、账号或APP数据，保留现有1/2/3接入配置。真实冷启动不在本轮验证内。

## 最小方案与取舍

保留现有Host纯策略和桌面确认路径，将明确不足单独计算。更简单的仅排除未知但保留90%弹窗仍不符合需求；完全删除检查则会丢失实际不足确认，均未采用。无依赖新增或数据迁移。

只在有效JSON缺少RAM字段时，读取同编号leidian.vbox，严格限定VirtualBox/Machine/Hardware/Memory直属路径和http://www.virtualbox.org/命名空间。文件限1MiB、深度32，禁DTD及外部解析器，不读取备份或快照。两个有效来源不一致则未知；明确无效/重复的JSON字段不被XML回退绕过。有效JSON但现有XML损坏/锁定时，保留单一已知JSON数值并提示第二来源未核验，不宣称两源一致。

VirtualBox官方[设置读写源码](https://raw.githubusercontent.com/VirtualBox/virtualbox/main/src/VBox/Main/xml/Settings.cpp)将RAMSize映射到ulMemorySizeMB，[SDK参考](https://download.virtualbox.org/virtualbox/6.0.4/SDKRef.pdf)说明内存字段单位为MB。本工程按现有MiB约定换算；雷电路径和格式是本机观察结果，不冒充雷电稳定官方API。
